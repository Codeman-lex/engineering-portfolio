# Engineering decisions

1. **One Python process.** Streamlit handles navigation, forms and plotting. The generator, feature transform, scoring and storage modules run independently in pytest. This keeps local setup to one command after dependency installation.
2. **A fixed synthetic ledger.** Stable identifiers and a seeded stream make investigations reproducible. USD-only amounts keep volume totals meaningful. Profiles differing in activity and spend create variation within the same scenario. The stored rule scores use default settings.
3. **Chronological evaluation.** The split precedes model fitting and threshold estimation. An explicit seven-feature allowlist excludes labels, IDs, statuses, scores, future activity and injected scenario membership. The deployment demonstration uses one split and one seed.
4. **Two operational thresholds.** A rule category controls review priority, while a detector-specific cutoff controls evaluation. Keeping these separate lets analysts compare recall and review workload without rewriting cases.
5. **Cached reads and transactional writes.** Bootstrap loads the ledger and models once per process. Filtering uses Pandas, and the explorer sends at most 50 rows per page. Explicitly preparing large CSVs keeps serialization off routine reruns. SQLite serializes initialization and case edits. Revision checking prevents silent lost updates.
6. **Deployment scope.** A Python host runs Streamlit and its WebSocket session. The static and Worker formats supported by Sites cannot host this Python process directly. Streamlit Community Cloud is the documented target. Shared notes on ephemeral storage suit a synthetic demo. Durable multi-user operation would require identity, access controls, append-only audit history and a persistent database.
